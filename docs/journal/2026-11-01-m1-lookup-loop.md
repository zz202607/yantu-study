# M1 查题闭环（2026-11-01）

目标：拍照 → 识别题号 → 秒出题干/解析裁图。M0 的索引与裁题工具已就绪，
M1 只补「照片里的题号」与「手机网页」两块。

## 做了什么

- `tools/recognize_qid.py`：照片 → 题号候选（纯本地 OCR，不联网）
- `tools/eval_photo_qids.py`：18 张真图基准，文件名只当答案
- `app/server.py` + `app/static/index.html`：FastAPI + 手机优先单页
  - `/api/recognize` 上传照片 → 候选；`/api/resolve` 题号校验；
    `/api/crop` 裁图（`.cache/crops/` 缓存）；`/api/books` 书目
- 题干走**空白册**、解析走**案例习题集**（C 族对照本）；Z 族题目答案同页

## 关键发现（踩过的坑）

1. **RapidOCR 的检测框坐标在「预处理后」的图像空间**，不是输入图像素。
   必须乘 `op["preprocess"]["ratio_w/ratio_h"]` 才能回到原图；
   否则裁出来的图会「张冠李戴」（一开始按框裁到的是别的行）。
2. **题号那一行经常整行漏检**：红圈、横穿笔迹叠在行首时，DB 检测器会把整行丢掉，
   提高分辨率/降阈值都救不回来。但**窄窗 OCR**（沿左边距滑窗）读得很干净。
   → 最终三路合流：检测框裁切 + 向左扩到页边 + 左边距滑窗。
3. 识别模型的输入宽度固定（3×48×320），长条会被压缩，**行首题号最先被挤掉**；
   滑窗必须**窄**（约 4–6 个字宽），宽窗兜底题号印得偏右的情况，两路都要。
4. 题号残读很常见：`p=143-2`、`(412)`、`20419某`（红笔/手写粘连）。
   不做模糊纠正，改用**当前册题号集合唯一解**：给候选按索引校验，
   能唯一落地的才收，落不了就走手输——「宁可多问一次，不可记错」。
5. 自动入库规则与基准一致：**唯一 `start` 且 score ≥ 0.90、领先第二名 ≥ 0.05**。
   18 张真图里触发 5 次，5/5 全对；其余进候选让人点。
6. 方向：EXIF 转正后先按「检出文本行数」判断要不要再转 0/90/180/270；
   绝大多数照片 EXIF 已正，直接跳过搜索（省 ~1.5 s）。

## 基准结果

- 候选召回 **17/18 = 94%**（目标 95%，差 1 张）
- 自动入库 **5/5 全对**（目标 98%）
- 唯一漏网：`4-21错.jpg` —— 红圈手写压在题号上，OCR 稳定读成 `21` / `4-31`；
  按产品原则走手输，不猜
- 速度 8–15 s/张，偏慢；瓶颈是两路滑窗（各 ~1–3 s）+ 整页检测 (~3 s)。
  下一轮：先检测通道，命中高置信就跳过滑窗；滑窗降步长/降宽度
